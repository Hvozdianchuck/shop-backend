# Event contracts: Avro and Schema Registry

Avro spec: https://avro.apache.org/docs/1.12.0/specification/
Schema Registry: https://docs.confluent.io/platform/current/schema-registry/index.html
Evolution and compatibility: https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html

## Why

- In v1 each service had its own JSON records. A rename on one side broke the other only at runtime.
- Now the schema is the contract: `.avsc` files in `contracts`, classes generated by `avro-maven-plugin`
  (`stringType=String`, `enableDecimalLogicalType=true`). Generated code is in `target/`, not in git.
- Sharing the schema is not sharing domain code. In separate repos each service would generate classes from
  the registry (or a schema artifact); one repo makes a module the simplest way.

## Wire format

- Confluent serializer: magic byte 0, 4-byte schema id, then Avro binary. No field names in the message.
- Producer registers the schema (`auto.register.schemas=true` by default, fine locally; in production schemas
  are usually registered by CI and producers run with auto-register off).
- Consumer fetches the writer schema by id and resolves it against its own reader schema
  (`specific.avro.reader=true` → generated classes).
- Avro 1.12 refuses to instantiate classes from untrusted packages
  (`org.apache.avro.SERIALIZABLE_PACKAGES`). Here `shop.avro.trusted-packages` in `application.yml` registers
  `com.shop.contracts` (`MessagingAutoConfiguration`).

## Subject name strategies

- `TopicNameStrategy` (default): subject `<topic>-value`. One schema per topic.
- `RecordNameStrategy`: subject = record full name. Same type can be in many topics, compatibility per type.
- `TopicRecordNameStrategy`: `<topic>-<record full name>`. Several types per topic, each evolves on its own.
  Ours: `orders` holds `OrderPlaced` and `OrderCancelled`, and they must share the topic to stay in order.
- Alternative for several types: a union as the top-level schema with `TopicNameStrategy`. Every new type then
  changes the union.

## Compatibility modes

- `BACKWARD` (default): new schema reads data written with the last one. Allowed: add field with default,
  delete field. Upgrade consumers first.
- `FORWARD`: old schema reads data written with the new one. Allowed: add field, delete field with default.
  Upgrade producers first.
- `FULL`: both. Add/delete only fields with defaults. Any order.
- `*_TRANSITIVE`: check against all previous versions, not only the last. Matters when old data stays around
  (compacted topics, long retention).
- `NONE`: no checks.

## Evolution rules (Avro)

- Field matching is by name. Rename = delete + add; use `aliases` to keep reading old data.
- Default value is what makes add/delete safe.
- Allowed type promotions: int → long, float, double; long → float, double; string ↔ bytes.
- Enums: adding a symbol breaks old readers unless the enum has a `default`.
- Logical types: money as `decimal` (bytes, precision 12, scale 2) here, never `double`.

## In this repo

- `OrderPlaced` v2 got `currency` with default `"EUR"`. `SchemaCompatibilityTest` registers v1 (copy in
  `src/test/resources/schemas`), checks v2 passes, and that a new required field gives `409`.
- Metadata (`eventId`, `eventType`) is in Kafka headers, not in the schema.
